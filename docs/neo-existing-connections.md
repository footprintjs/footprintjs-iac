# Neo as a consumer of connection profiles

Neo's integration composes the base `ConnectionProfileRegistry`, profile-store and secret-store contracts. The base registry, workflow and Lens form have no Neo-specific branches. The identity wrapper supplies the adapter schema, the trusted endpoint policy and actual service checks.

Open an existing-resource flow with `{ mode: 'existing', profiles: 'user', details: 'human', id: '<new-flow-id>' }`. The returned `connectionProfiles` catalog supplies Lens with the adapter-declared form and saved profiles. Register a profile with the existing OIDC issuer, the `neo-checks` validation client, an existing validation account and its password. Registration checks discovery and authenticates that account before saving the profile. A failed check does not create a usable profile.

Start with `workflow.start({ profileId })`. The base workflow binds the immutable profile ID before Find. The Neo adapter resolves that user's address and secret references, checks the approved service, and observes the existing directory/provider without applying or importing either resource. Human mode then pauses at Connection details. Resume with the exact pause token and the same profile ID; a different profile requires another workflow. Connect applies only Neo's four consumer resources. Verify performs the existing connection, login and allowed/denied access checks.

The user-entered issuer supplies Neo's `JWT_ISSUER` and `OIDC_AUTHORITY`. The validation password proves access to the existing source; it is not a Neo application client secret and is not inserted into deployment specifications. The browser application continues using its public `neo` client with authorization-code/PKCE. Password-grant validation is restricted to the explicitly enabled check client in this local trial; it is not a general enterprise login recommendation.

This local adapter admits only the exact identity issuer in the prepared target before any outbound request. It demonstrates user-entered configuration against a real existing service while preserving ownership and endpoint controls. Supporting an arbitrary company identity provider requires a host-approved adapter and endpoint/trust policy; editing a browser URL does not authorize a new destination.

Safe profile settings and opaque secret references are append-only records under `<target>/connection-profiles`. Secret values are encrypted by the local secret adapter under `<target>/connection-secrets`; its private local key is also owned by the host. This is a laptop storage implementation. Production hosts can provide a different `SecretStoreAdapter` and profile store through the composition boundary. Existing generated fixture credentials remain private fixture inputs, separate from newly registered profiles.

The master/workflow state and native FootPrint recordings retain the selected profile ID, safe endpoint, opaque credential reference, measured stages and outcomes. Neither passwords nor validation access tokens enter workflow scope, native records, HTTP responses or profile JSON.

Use `connectionProfiles.test(profileId)` for a fresh measured check of the saved profile. Resolving it at Find, after resume and during validation checks the current service again. Authentication may create normal identity-provider audit/session events, but Find never changes infrastructure or source configuration.

After the workflow completes, rechecks separate **binding admission** from **availability measurement**. They still verify the immutable saved profile, approved issuer/client/account, source physical identity and target scope. They do not authenticate through the profile registry before launching the actual connection/access checks: otherwise an outage would abort before its failures could be recorded. The check adapters then measure the unavailable service and retain their failed native runs. Later successful checks create distinct recovered runs; they do not overwrite the failed observations or rewrite the completed parent deployment.

The local example also returns fixed `pauseIdentityService()` and `restoreIdentityService()` controls. These are separate, explicitly configured tests against this trial's **owned** provider, implemented through `applyNeoIdentityFault`. They retain the provider container and data, and cannot select an arbitrary resource. Find itself does not adopt or mutate an existing source. Each test action retains native engine evidence plus a flow-local fault reference. The action and subsequent observations remain separate recordings: temporal correlation does not manufacture a native cross-run causal dependency or prove unobserved provider internals.
